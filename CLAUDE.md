# Working on this project

**Read [TASHFIN-PORTFOLIO-CONTEXT.md](TASHFIN-PORTFOLIO-CONTEXT.md) before
doing anything else.** Do not start work, answer a question about the site, or
open any other file first. It holds who the work is for, how the site is
built, what has already been decided, the traps already hit, and the current
state. Reading it is not optional and it is not a formality: nearly everything
in it was learned the expensive way.

`TODO.md` holds what is still to do. `DEPLOY.md` holds the commands.
`LINKEDIN.md` holds the LinkedIn text, ready to paste.

## Write everything down, as you go

Tashfin compacts this conversation often, on purpose. Anything that exists
only in the chat is gone the moment he does. **The conversation is not
memory. These files are.**

So, after each piece of work, before moving on:

1. Put what changed into `TASHFIN-PORTFOLIO-CONTEXT.md`. Something learned the
   hard way goes under **Traps already hit**; something settled goes under
   **Decisions already made**; what is now live goes under **Current state**.
2. Move anything outstanding into `TODO.md`, with enough detail to act on
   without asking him again. If you drafted a piece of text for him, the text
   itself goes in, not a description of it.
3. Commit the files with the work, in the same commit.

Do this at the end of each piece of work, not at the end of the session. A
session can stop at any moment.

**Anything he tells you in conversation that the next session would need gets
written down too**, not just acted on. Which district, which detail is out of
date, what he decided about the agency. If he says it and it matters, record
it.

## How he wants things written

First person, short sentences, concrete nouns. No aphorisms, no em-dashes
standing in for full stops, nothing pleased with itself. He dislikes
AI-sounding prose and will say so.

**Never invent a figure.** He has none to give yet. Argue from method instead.
A true sentence with fewer specifics beats a sharp one built on invented data.

## How he works

He is not a developer. Do the technical work for him and explain it plainly.
He asks in very short messages and expects the obvious next step to be taken
without another round of questions. When he cannot supply something,
restructure the work so it does not depend on it rather than stalling.

Verify rather than assume: check the live URL, the rendered DOM, the API —
not the form that looked like it saved. Say plainly what failed or went
unchecked. Ask before anything that publishes in his name.
